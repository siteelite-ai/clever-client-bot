# Ответы на уточнения: корректировка после браузерного прогона 3 ноября

База: опубликованный main `9202318a875c0f1f14455cf3f8a51b6ad6d5221a`.
Проверенная до исправлений frontend-версия: `widget-26ebaed1b19f076d`.
Область: только backend и локальные регрессионные тесты. Frontend, модели,
бюджеты вызовов, секреты, БД, MODX и production-настройки не меняются.

## Доказанные проблемы

- Кабель для земли: после признания «марку и сечение не знаю» повторялся тот же
  вопрос. Инженерную границу MVP сохраняем; повторный запрос неизвестных данных
  заменяем объяснением и существующим контактом менеджера.
- Кабель для насоса: маркировка в фразе «В проекте указан КГ 3*1,5. Проверь
  наличие и цену» не принималась. Требовался голый машинный формат.
- Автомат двигателя: в составном ответе «Прямой пуск, номинальный рабочий ток
  по шильдику 6 А» терялось владение током — название нагрузки было в предыдущем
  подтверждённом ходе, а локальный разбор смотрел только текущий.
- После отдельного «6 А» категория находилась, но напряжение не было покрыто
  каталожной проверкой, затем коррекция отклонялась как `invalid_critical_input`.
  Старый лог не содержит ошибочного поля/impact, поэтому точную разновидность
  последнего нарушения по нему установить нельзя. Не объявляем её доказанной.

## Общие изменения

1. Приём явно заявленной спецификации с обозначением источника (паспорт,
   проект, шильдик, маркировка) для любых семейств кабелей. Разбирается вся
   фраза, а не удобная подстрока. Отрицания, альтернативы, неопределённость,
   второй товар и дополнительные ограничения не отбрасываются ради shortcut.
2. Все конкурирующие compound-маршруты проверяют один и тот же скомпилированный
   запрос. Иначе слова источника могли повторно трактоваться как свойство
   товара соседним semantic-поиском. Обычные запросы без такого verified-ответа
   сохраняют прежний вход.
3. Составной ответ сохраняет владельца измерения из подтверждённого запроса.
   Защита от подмены тока нагрузки номиналом автомата/кабеля остаётся в обоих
   местах: готовности к поиску и владении числовыми фильтрами.
4. Для уже подтверждённого цитатой факта длина повторного модельного объяснения
   `impact` не определяет готовность. Поле остаётся типизированным и ограниченным;
   для неизвестного факта сохраняются прежние требования к объяснению и вопросу.
   Это не доказательство пригодности товара и не отключение числовых проверок.
5. Отказ проверки товара отделён от запроса данных клиента. Если данные уже
   приняты, бот не просит повторить их; при доступном диагностическом сигнале
   называет непроверенный тип параметра и даёт только контакт из базы знаний.
6. В диагностике нарушения входного контракта — имя поля, тип и длина вместо
   одного общего кода. Текст модельного объяснения не журналируется.

Никаких новых SKU, словарей брендов, подстановки токов/сечений, ослабления
проверки напряжения или увеличения числа LLM-попыток не добавлено.

## Регрессионные проверки

Сначала новые unit-тесты воспроизвели три дефекта на старом коде. Затем добавлены:

- различные семейства, десятичные разделители и формулировки источника;
- отрицательные случаи: отрицание, вопрос о пригодности, несколько маркировок,
  второй товар, цена/другие ограничения, новая тема, неподтверждённый слот;
- ответ «не знаю» → контакт → позднее указанная маркировка → карточка каталога;
- питание → единый ответ о пуске и токе → поиск допустимых диапазонов;
- запрет интервала, не включающего ток, и запрет точного номинала вместо нагрузки;
- известный факт без повторного impact, но отказ для неизвестного/чужой цитаты;
- непроверенное напряжение → нет карточек, понятное объяснение, не новый вопрос.

HTTP/SSE-fixture теперь запускает настоящий обработчик с включённым
`VOLT220_SELECTION_READINESS_REQUIRED`, как production, а не только старый OFF.
Все обращения к модели/каталогу в этих тестах синтетические и не расходуют квоту.

## Что НЕ считается закрытым

Новый live-прогон после этой корректировки ещё не выполнен. Синтетический PASS
не подтверждает реальные характеристики склада и не закрывает весь клиентский
набор. В частности, строгая пригодность автомата по напряжению остаётся
обязательной: если её нельзя доказать карточкой, это объяснённая передача
менеджеру, а не успешный автоматический подбор. Следующий узкий preview-прогон
должен отдельно проверить реальную выдачу двигателя и точный контрольный поиск.

До положительного preview-результата не делать merge/deploy production.
Откат изменения — revert одного PR; миграций, переключений моделей, ключей
или клиентского JS в нём нет.
