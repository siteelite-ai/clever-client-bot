# PR #121: граница проверки PostgreSQL

CI запускает одноразовую PostgreSQL 16 и применяет **настоящие** миграции,
которые создали `chat_request_logs`, добавили идемпотентность и ввели два
механизма admission. Затем применяются три миграции PR #121. Минимальные
заглушки `auth.uid()` и `has_role()` нужны только для разбора старых RLS-политик
в обычном PostgreSQL; они не имитируют Supabase Auth. Права `service_role` на
журнал также явно добавляются в тестовой БД, поскольку обычный PostgreSQL
не получает их из настроек Supabase.

Проверяются: сохранение колонок, индекса идемпотентности, RLS-политик и
lazy-GC-триггера; nullable/default-off привязка новой темы; прежняя запись
журнала; новая legacy-запись без темы; существование прежних admission RPC;
отдельные тесты прав, fencing, replay и конкурентного начала диалога.

Это **не** полный replay 50 исторических миграций и **не** доказательство
совместимости с живой схемой или отсутствия блокировок при `ALTER TABLE`.
Ранняя история требует pgvector и Supabase Auth. В одной из старых миграций
есть литерал токена каталога; перед полным replay на внешнем CI нужен
отдельный security follow-up: установить, был ли токен рабочим, при
необходимости отозвать его и очистить историю.
Тест также не охватывает более позднее ужесточение прав на GC-функцию,
поскольку его миграция затрагивает и другие подсистемы. Проверяется только
сохранение старого GC-триггера на журнале. До применения к рабочей БД нужны
отдельные сверка схемы, rehearsal блокировок и план отката.
