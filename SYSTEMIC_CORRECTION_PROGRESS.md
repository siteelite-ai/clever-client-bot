## Где мы сейчас

- **Сейчас:** этапы 3–5 — числовые условия привязываются либо к самому выбираемому товару, либо остаются контекстом применения; одно и то же доказательство больше не дублируется в публичном контракте.
- **После этого:** этапы 3–5 — закрыть оставшиеся детерминированные дефекты матрицы теми же контрактами, без товарных словарей и веточных исключений.
- **Затем:** этапы 6–7 — повторный полный прогон 27 сценариев, вариаций, сохранённых сессий и браузерных тестов с контролем времени.
- **Контрольная точка перед PR:** этапы 2–7 должны быть проверены, а не просто реализованы; критические сценарии проходят не менее трёх раз.
- **Production:** не затрагивается до этапа 9 и отдельного подтверждения финальной приёмки.

- [-] **3. Единый контракт намерения и критериев**
  - Ввести типизированный контракт: товарный класс, применение, ограничения, бюджет, количество результатов и происхождение каждого критерия.
  - Разделить требования пользователя, безопасные вычисления, предположения и каталожные факты.
  - Запретить неподтверждённым предположениям становиться обязательными фильтрами.
  - Готово, когда ложные критерии вроде «для ЖКХ» не появляются без запроса пользователя.
  - Добавлено происхождение критерия: явное условие пользователя, обязательный вывод, подтверждённый факт каталога или предположение модели.
  - Предположение модели теперь может направить первичный поиск, но не попадает в неизменяемый обязательный контракт и не исключает товары без подтверждения клиента.
  - Явные отрицательные условия клиента сохраняются отдельно и остаются обязательными.
  - Финальное совпадение характеристик карточек больше не может само создать новое обязательное условие; контракт отдаёт происхождение каждого обязательного критерия.
  - Приёмочная матрица автоматически отклоняет карточки без контракта происхождения и критерии с происхождением «предположение модели» или «факт каталога».
  - Любая ветка, отдающая карточки, теперь обязана отправить машинный контракт; отсутствие обязательных критериев представляется честным пустым контрактом, а не скрытым состоянием.
  - Прямой поиск точной составной маркировки отдаёт явный пользовательский критерий `3×1,5`; preview-проверка пройдена дважды.
  - Общее слово больше не повышает составное каталожное значение до требования клиента: все значимые части значения должны быть подтверждены запросом. Это устраняет ложную привязку к «ЖКХ» без товарного словаря.
  - Явное назначение в конструкции `для …` компилируется только в уникальное значение живого фасета. Preview 430 трижды подтвердил контракт `Philips + офисно-административное освещение`; неоднозначное или отсутствующее значение не превращается в фильтр.
  - Общий морфологический гард больше не считает любую замену одной буквы доказательством: `светом` не может включить фасет `свеча`. Технические коды с визуально похожими кириллическими/латинскими символами нормализуются единообразно (`Е27` = `E27`).
  - Связанный с классом товара клиентский qualifier теперь обязан либо подтвердиться живым фасетом, либо перейти в лексическое сопоставление. Быстрый фасетный поиск больше не может бесшумно потерять слово вроде `кукуруза`; правило не содержит словаря товаров и применяется к любому классу.
  - Для короткого изменения атрибута введено общее правило фасетов: значения текущей реплики заменяют наследованные значения только на том же живом ключе; все прочие подтверждённые ключи сохраняются. Морфология коротких русских прилагательных (`белый`/`белые`) обрабатывается структурно, без словаря цветов.
  - Эквивалентные числовые доказательства из живого фасета и текстового восстановления объединяются в одно обязательное условие. Одинаковые числа на разных независимых осях при этом не схлопываются.
  - Preview 450 подтвердил чистый контракт автомата: ровно три условия — `Количество полюсов = 1`, `Характеристика срабатывания = C`, `Номинальный ток = 25 А`; прежние дубли `25` и `A = 25` отсутствуют.

- [-] **4. Связка «рассуждение → поиск → проверка → выдача»**
  - Поиск должен исполнять тот же контракт, на котором основано объяснение.
  - Проверить привязку чисел, единиц и свойств: В, А, кВт, фазы, полюса, цоколи, сечения и размеры.
  - Не допускать подмены товарного класса: лампа/светильник, силовой/слаботочный кабель и т. п.
  - Готово, когда правильное рассуждение приводит к соответствующим товарам или честному уточнению.
  - Для успешной выдачи без текста провайдера сервер строит видимое обоснование только из уже проверенного товарного класса и обязательного контракта.
  - Preview 421 подтвердил появление видимого обоснования и машинного контракта у пяти карточек; проверка сценария гостиной остановлена внешней квотой.
  - Preview 430 подтвердил сквозную связку назначения: фраза клиента `для офиса` → живой фасет `Вид светильника = офисно-административное освещение` → поиск с брендом Philips → две карточки, прошедшие тот же контракт.
  - Preview 433 устранил подмену класса в аналогах без словаря товаров: полное описание источника и его живое таксономическое пространство замораживаются до поиска кандидатов. Сценарий лампы GX53 прошёл 3× за 2,3–2,6 секунды, каждый раз вернул четыре лампы и ни одного светильника.
  - Точный счёт в одном фасете теперь сверяется и с видимой составной маркировкой: при `ровно 1 полюс` карточка `1П+Н` отклоняется, даже если старый структурный фасет каталога хранит её как `1`. Сценарий 25 A / C / 1П прошёл 3×.
  - Preview 437 сквозным контрактом связал явные `3000 K`, `тёплый`, `E27` и `светодиодная` с поиском и карточками. Сценарий прошёл 3×: четыре лампы E27/3000 K, без ложной `свечи` и без лишнего внешнего AI-вызова.
  - Измерение применения больше не может присвоиться безразмерному товарному фасету только из-за совпавшего числа: высота монтажа `1,5 м` не становится `Вес = 1,5`. Ошибочная выдача блокируется до карточек.
  - Прямое измерение самого выбираемого товара теперь сохраняется без предметного патча: конструкция `автомат на 25 А` допускает точный живой фасет, а `для нагрузки 25 А`, площадь и высота монтажа не становятся свойствами товара. Короткий технический код `C` принимается только при единственном однозначном совпадении с живым фасетом; обычная русская предлоговая `с` кодом не считается.
  - Preview 450 повторно провёл квартиру через уточнение к четырём точным карточкам 1P/25A/C за 4,1 секунды; противоположный сценарий прожектора зафиксировал `direct_measured_criteria = 0` для площади 35 м² и высоты 1,5 м.
  - Для многословных живых категорий добавлен общий schema-aware resolver: сокращённый класс клиента допускается только при безопасном head-совпадении, а несколько веток с тем же head различаются минимум двумя уникальными фасетными осями. Формулировка `автомат` теперь выбирает `Автоматические выключатели` по `Количество полюсов + Характеристика срабатывания`, а не по словарному алиасу; при одном признаке или равенстве оценок resolver отказывает.
  - Доказанный короткий head передаётся дальше как активная товарная цель. Это устраняет разрыв, при котором категория уже была проверена живой схемой, но оркестратор всё равно повторно запрашивал модель.

- [-] **5. Количество, ранжирование и уточняющие вопросы**
  - Единообразно обрабатывать «самый дешёвый», «несколько», «варианты» и «все позиции».
  - При недостатке результатов расширять поиск только внутри того же товарного класса и без снятия обязательных условий.
  - Не спрашивать уже указанные параметры и не требовать от покупателя лишней технической теории.
  - Готово, когда количество карточек и уточнения соответствуют запросу во всех товарных категориях.
  - Подтверждён общий, не привязанный к категории контроллер количества: «самый дешёвый»/«один» → 1; обычный подбор → цель 4, минимум 3; «несколько/варианты» → цель 5, минимум 3; «все» → расширенная выборка до 8; явное число → указанное число в безопасном диапазоне.
  - До финального ограничения контроллер расширяет окно поиска и проверяет до 15 кандидатов для цели 5, поэтому отсеянные карточки могут быть заменены следующими подходящими без ослабления критериев.
  - Каждый товарный ответ теперь содержит машинный контракт `result_cardinality` с полями `target`, `minimum`, `mode`, `explicit`; он добавляется и к прямым веткам, которые обходят основной agent-loop.
  - Приёмочные сценарии для светильников, розеток, автоматов, удлинителей и одиночного суперлатива проверяют не только фактическое число карточек, но и решение контроллера о требуемом количестве.
  - Preview 423 подтвердил контракт одиночного суперлатива на живом API: одна точная карточка, `target=1`, `minimum=1`, `mode=single`, 5 065 мс. Preview 426 трижды подтвердил многотоварный контракт: пять карточек, `target=5`, `minimum=3`, `mode=alternatives`.
  - Множественный суперлатив больше не схлопывается до одной карточки. Если строгий каталог подтверждает меньше желаемого минимума, критерии не ослабляются: preview 430 трижды вернул все две офисные позиции Philips и явно сообщил о дефиците относительно цели 4.
  - Прямой запрос `покажи все позиции` сохраняет расширенную кардинальность после очистки командной части точной маркировки: preview 431 трижды вернул восемь точных ВВГ 3×1,5 с контрактом `target=8/minimum=3/mode=exhaustive`.
  - Остаётся системная работа по уточнениям: текущий ранний readiness-слой содержит предметные профили. До финала его нельзя считать универсальным; нужно заменить либо ограничить его общей проверяемой политикой «какой недостающий параметр действительно меняет совместимость/диапазон выбора» и живыми фасетами.
  - Точно заданный availability-запрос больше не блокируется необязательным вопросом о уже указанном параметре; сценарий `3000 K + E27` сразу переходит к каталогу.
  - Инженерный вопрос с явно указанной измеряемой нагрузкой сначала допускается к видимому расчёту и допущениям, а не блокируется перечнем финальных каталожных полей. Прямая команда покупки с неполными параметрами сохраняет строгий readiness-гейт.
  - Исправлена общая причина преждевременного поиска после уточнения: readiness теперь извлекает доказательства только из реплик пользователя и никогда не засчитывает перечисленные самим ассистентом параметры как уже сообщённые клиентом.
  - Контракт уточнений вычисляет список реально незаполненных параметров. На следующем ходе он продвигается к недостающим данным, а не повторяет первый вопрос и не отправляет неполную задачу в каталог.
  - Локальная проверка нового перехода и общих контрактов: 646 из 646 V3-тестов пройдены; проверка типов основной функции пройдена.
  - Preview 444: сценарии кабеля насоса и автомата двигателя прошли по 3×. Все 12 ходов сохранили исходную задачу, не выдали товары до обязательных данных и задали только следующий недостающий вопрос; прогретые ответы заняли 0,44–0,66 секунды.
  - Числовые ответы вида `35м2 и высота 1,5м` теперь закрывают те же измеряемые поля, что и ответы со словами «площадь» и «высота»: preview принял уточнение, перешёл к категории прожекторов и нашёл 42 кандидата. Финальный render пока остановлен внешней квотой и не засчитан как положительная выдача.
  - Для квартирного автомата отключающая способность переведена из блокирующего поля в явно запрашиваемое проектное пожелание: базовый подбор не должен зависать без него. Сценарий `25 А → характеристика C, 1 полюс` снова прошёл 3× с четырьмя карточками 1P/25A/C и без `1P+N`.

Именованные параметры применения по-прежнему не проходят этот путь.
  - Односимвольный токен после числа распознаётся как единица измерения, а не технический код: в `16 А характеристика С` больше нет ложной конкуренции `A` против `C`. Строчная кириллическая `с`, неоднозначные оси и коды без названного фасета остаются запрещены.
  - Preview 456: прямой запрос автомата до 1 000 ₸ прошёл 3× за 3,2–3,8 секунды, каждый раз вернул четыре карточки 1P/16A/C. Соседний двухходовый сценарий 25A/C/1P также прошёл 3× за 4,3–4,8 секунды.
  - Защитная диагностика аварийного отключения сохраняется в продолжении диалога. Сценарий `выбивает автомат → 5 кВт, нет дифавтомата` прошёл 3× без карточек и без опасного назначения номинала; однофазный ток помечен только как расчётное допущение, запрашиваются фаза, автомат, кабель и режим срабатывания.

- [-] **6. Производительность и внешние ограничения**
  - Ограничить число последовательных AI- и каталожных вызовов.
  - Ввести общий временной бюджет, контролируемые повторы и понятную деградацию при квоте.
  - Отделить логический «товар не найден» от сетевой ошибки и внешнего лимита.
  - Готово, когда тесты укладываются в согласованный лимит и не зависают на минуты.
  - Трассировка прежних успешных прогонов показала первопричину задержки: 20,9–23,6 секунды уходили на первый вызов модели, который не давал рассуждения и только сериализовал уже обязательный `discover_category`.
  - Обязательное начальное discovery теперь компилируется сервером из исходного запроса; очевидная категория выбирается консервативно только по живому дереву каталога. При неоднозначности остаётся прежний модельный resolver, поэтому словаря товаров и угадывания категории нет.
  - Preview 426 прошёл три из трёх изолированных прогонов запроса о нескольких светильниках с датчиком даже при недоступной внешней квоте: пять карточек каждый раз, 7 818 / 3 990 / 3 731 мс по клиентскому таймеру и 6 145 / 3 560 / 3 384 мс по серверному журналу. До исправления тот же маршрут занимал 25 175–30 731 мс.
  - Preview 427 прошёл тот же подбор внутри сохранённой сессии после карточки кабеля: шесть из шести товарных ответов по светильникам за 2 654–3 511 мс, по пять карточек в каждом. Языковой resolver различает головной товар и зависимый параметр (`светильник с датчиком`, `кабель для насоса`) по структуре фразы, а не по словарю категорий.
  - `upstream_quota_exceeded` отделён от пустого каталога и возвращает отдельное понятное сообщение; квота сейчас блокирует полный живой прогон.
  - Проверка API OpenRouter 28 сентября показала фактический остаток `-0,199572384` кредита (`670` пополнено, `670,199572384` использовано). Поэтому модельно-зависимые сценарии объективно не могут завершиться до пополнения либо отдельного разрешения резервного провайдера.
  - Реализован ограниченный provider-failover: только для `402/408/409/429/5xx`, с сохранением тех же сообщений, tool schemas и обязательных post-gates; ошибки авторизации/валидации не скрываются. Резервный Lovable AI Gateway выключен по умолчанию и не будет активирован без отдельного согласия на передачу ему текста запроса и ограниченного каталожного контекста.

## Текущий итог

Пройдены этапы 0 и 1. Этапы 2–7 находятся в работе. Изменения product-кода есть только в изолированной ветке и preview 456; production остался на версии 433. Локально пройдены 667 V3-тестов и проверка типов основной функции. Подтверждены 13 из 27 клиентских сценариев; автомат 1P/16A/C до 1 000 ₸ и соседний автомат 25A/C/1P прошли по 3× после сквозного schema-aware исправления. Первый из них дополнительно прошёл через реальный браузерный виджет: четыре корректные кликабельные карточки, восстановление истории после перезагрузки и рабочие элементы управления. Preview-сценарии насоса, двигателя, защитной диагностики и изменения `чёрные → белые` также прошли по 3×; отдельно подтверждено отсутствие ложной проекции высоты в свойства прожектора. Полный положительный API-прогон требует восстановления основного баланса OpenRouter либо отдельного разрешения резервного провайдера: фактический остаток сейчас отрицательный. Детерминированные серверные ветки продолжают проверяться без внешней модели. Сценарии Philips/офис, полный список ВВГ 3×1,5, аналоги лампы GX53 и тёплые LED-лампы 3000 K/E27 ранее также прошли по 3×.
