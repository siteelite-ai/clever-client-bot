# PR #121: NO-GO для включения состояния диалога

**Состояние на 20.10.2026:** NO-GO для runtime и production. Пять миграций и gateway в PR #121
создают только отключённую основу. Атомарные `claim+begin` и `finish` уже
проверены на одноразовой PostgreSQL 16 и доступны в шлюзе, но `chat-consultant-v3/index.ts` не импортирует
gateway или новый проектор контракта. Новый чистый проектор
`conversation-selection-snapshot.ts` проверяет, что успешный завершённый лог
той же темы переносит исходный запрос, обязательные критерии и URL уже
показанных карточек через два информационных уточнения к четвёртому запросу
«А есть другие варианты?». Детерминированный тест без OpenRouter доказывает
структуру переноса и отказ при чужой теме, истечении срока, неподтверждённом
логе и повреждённом контракте. Отдельный тест смены товарного домена
подтверждает, что новый запрос кабеля не получает критерий площади люстры.
Это **не** доказывает поведение живого бота.
У зафиксированного production-сценария `selection_contract.mandatory_criteria`
пуст, а нового сертификата в логе нет: проектор не превращает этот уже
записанный лог в пригодный контракт и сам по себе не исправляет четвёртый ход.

Подготовлен отдельный **чистый server-only** сертификат
`server_destination_fit_proof`: его можно сформировать лишь из исходного
запроса и **точных показанных `ProductFull`**, заново проверив каждую карточку
существующим `verifyReplacementDestinationFit`. Сертификат связывает запрос,
хеш selection-контракта и идентификаторы/URL всего показанного блока.
Проектор принимает пустые `mandatory_criteria` для измеренной замены только
при валидном сертификате, переносит его через информационные уточнения и
добавляет новые URL лишь после отдельного доказательства нового блока.
Неподтверждённая карточка, неверный состав блока или смена темы сбрасывают
продолжение. Это **не** равенство фасета «зал = гостиная» и не разрешение
показывать старые карточки без нового поиска. `index.ts` пока не создаёт
сертификат на границе финального рендера и не подключает проектор, поэтому
production-сценарий остаётся NO-GO.

## Почему нельзя просто подключить один вызов в обработчике

1. В текущем протоколе виджета есть `sessionId`, но нет отдельного случайного
   bearer темы и версии. `sessionId` задаётся браузером и не может разрешать
   чтение серверного состояния. Первый bearer должен появиться в бесплатном
   JSON pre-turn handshake **до** платного запроса: потерянный первый SSE
   иначе сделает replay невосстановимым. Bearer не выводится в диагностике,
   логах и URL. При включённом server flag старый кэшированный виджет без
   явного `conversationProtocol:1` должен идти прежним legacy-путём;
   некорректный opt-in — завершаться до платной работы.
2. Новый SQL `claim_and_begin_chat_v3_conversation_turn` атомарно создаёт
   строку `chat_request_logs` с `chat_v3_topic_id` и захватывает ход. Сейчас
   обработчик всё ещё вызывает старый `claimTurnLogStart` без этой привязки:
   новый RPC ни разу не применяется к живому запросу. Повтор уже занятого
   `messageId` должен сравнить topic/session/query и воспроизвести ответ
   **до** проверки свежести версии: потерянный SSE не должен превращаться
   в новый платный поиск или ложный 409.
3. Новый `finish_chat_v3_conversation_turn` умеет одной транзакцией сохранить
   terminal log и снимок. Но `finalizeLogAwait` в `index.ts` (около строки
   23122) всё ещё помечает лог завершённым перед UPDATE и проглатывает его
   ошибку; публичный terminal SSE может выйти без durable log. Нужно
   подключить новый RPC ко всему opt-in маршруту и удерживать публичный
   успех до подтверждённого commit. Ошибки и обрывы не двигают снимок.
4. Текущий автоматический `new_task` определяется уже **после** claim
   (около строк 22973 и 23627). Он может оставаться в том же SQL
   transport-topic, но старый selection необходимо очистить **до** поиска,
   ранжирования и prompt: семантическая новая задача не наследует прежний
   товарный домен. Явная кнопка «Новый диалог» отдельно вращает SQL-тему
   через pre-turn handshake.
5. Даже после подключения нельзя считать URL из предыдущего ответа
   разрешением к показу. Это только исключения для нового поиска. Каждая
   дополнительная карточка должна заново пройти поиск и все обязательные
   критерии. Если последняя выборка не содержит доказанного контракта,
   продолжение должно просить полный запрос, а не запускать свободный поиск.
   Сейчас `ellipticalBaseRequest` и `priorShownProductUrls` (около строк
   23860–23871) выводятся из `effectiveHistory`, то есть из клиента; для
   opt-in пути они должны исходить только из завершённых серверных логов.
6. Публичный `create_chat_v3_conversation` вставляет новую строку на каждый
   новый bearer и лишь вероятностно чистит истёкшие записи (миграция
   `20261020210200_chat_v3_conversation_rpcs.sql`). Handshake нельзя открыть
   без отдельного ограничения частоты/объёма create и reset: бесплатный
   запрос иначе создаёт неограниченную нагрузку БД. Resolve существующего
   bearer не должен расходовать модельную квоту.

## Минимальный целостный выпуск отдельным PR

- Добавить pre-turn handshake `{conversationProtocol:1,
  conversationAction:"ensure", bearer?}` на том же Edge endpoint. При OFF
  JSON `{enabled:false}` и прежний путь без новых полей; при ON
  `{enabled:true,bearer,version,expires_at}`. `reset` с bearer+version —
  только для явного нового диалога. Ограничить create/reset от злоупотребления.
- Для opt-in chat `{conversationProtocol:1,
  conversation:{bearer,version}}` связывать envelope с `messageId` и
  повторять неизменным при reconnect. В серверном entrypoint: replay до
  проверки версии, resolve до INSERT claim, topic id в самом INSERT,
  `begin` до платной работы; stale, expired и busy без второго OpenRouter.
- Составить доказанный непустой контракт во всех ветках показа, включая
  наблюдавшуюся legacy/direct люстру. На успешном завершении атомарно
  сохранить terminal log и CAS-снимок; при неуспехе — fail-closed. SSE
  `conversation_state` может содержать только новую версию после durable
  finalize; следующий ход снова делает ensure/resolve.
- Только затем подать снимок в общий selection route как
  `base_request + mandatory_criteria + excluded_urls`, не как свободный
  текст истории и не как подсказку модельной прозе. Старый off-path сравнить
  побайтно по публичным событиям.

**Гейт перед переключением:** пустой и непустой контракт на реальном логе;
disposable PostgreSQL concurrency/RLS тесты; детерминированные четыре хода,
смена товарного домена, forged history/slots/bearer, expiry, replay, два
параллельных хода и race reset/claim; preview 3× с реальными карточками и
QA-оракулом; проверка неизменности всех прежних логических веток. Лишь затем
отдельное решение о staged rollout и rollback. Пока эти этапы не пройдены,
PR #121 нельзя представлять как исправление четвёртого хода.
