## Дополнение: регрессия браузерной доставки

После завершения API-матрицы на встроенном в сайт виджете была обнаружена ошибка HTTP 400. Качество ответов backend, отражённое в матрице ниже, от этого не изменилось, однако первоначальная формулировка production-ready оказалась неполной: проверка не покрывала совместимость реально загруженного браузером публичного ассета.

Корневая причина: переход `messageId` на UUID был выпущен без изменения версии `widget.js`. Браузер мог продолжить исполнять закэшированный файл со старым ID вида `msg_<timestamp>_<random>`, который новая серверная валидация отклоняла.

Системное исправление вынесено в [PR #28](https://github.com/siteelite-ai/clever-client-bot/pull/28): ограниченная совместимость со старым форматом, очистка сохранённого клиентского состояния, содержательная обработка HTTP 400 и вычисляемый из содержимого кэш-ключ с обязательной CI-проверкой. Начиная с этого инцидента, финальный release gate включает не только API-матрицу, но и проверку живой цепочки `страница → embed.js → widget-version.js → widget.js → production endpoint`.

## Последняя найденная нестабильность и системное исправление

До PR #26 сценарий бытового светильника прошёл только 1 из 3 повторов:

- `a815d5e8-0193-43a2-816f-f4aaa1ad0c54` — потерян критерий датчика, показаны пять обычных светильников;
- `2e811a68-b4b0-4918-a49c-8a454856b503` — нарушен класс применения, показаны товары «для ЖКХ»;
- `e26d8461-7246-4687-918b-38086d4f2a56` — корректно найден Gauss HALL.

Корневая причина: полностью заданный запрос всё ещё проходил через длинный вероятностный цикл; модель правильно понимала критерии, но широкий поиск не всегда сохранял все оси до рендера.

Исправление: для явно заданного сочетания «бытовой + накладной + датчик + бюджет» введён ограниченный доказательный маршрут. Он:

1. не перехватывает неоднозначные запросы и сохраняет модельное рассуждение там, где требуется уточнение;
2. выполняет несколько ограниченных каталоговых запросов параллельно;
3. повторно проверяет цену, сенсор и класс применения по данным карточки;
4. запрещает подмену на ЖКХ, промышленное или уличное исполнение;
5. сохраняет факты реально показанной карточки для следующих вопросов.

После deploy отдельный smoke-test и два независимых набора 3× прошли полностью. В финальной матрице первый ход ускорился с 29–61 с до 0,9–1,6 с.

## Контур прикладной безопасности

Проверенная версия включает строгую схему входного запроса и лимиты размера и истории, защиту от утечки служебной механики, недоверие к истории ответов ассистента при маршрутизации критичных сценариев, рендер только карточек из серверного каталожного кэша, контролируемый домен товарных URL, доказательные гейты критериев и честный отказ вместо неподтверждённой рекомендации.

Оставшиеся эксплуатационные задачи, не блокирующие проверенные кейсы:

- модельный подбор аналогов DN027B всё ещё занимает 50–68 секунд; нужен отдельный SLO по быстродействию и оптимизация количества шагов;
- требуется мониторинг внешних зависимостей каталога и LLM, алерты по таймаутам и доле honest-empty;
- для формального security-sign-off отдельно нужны инфраструктурный pentest/DAST, проверка rate limiting/WAF, секретов и прав Supabase, а также нагрузочное испытание.
