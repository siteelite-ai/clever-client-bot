# Параллельный кабинет 220volt на server3

## Границы этого этапа

- Новый адрес: `chat-volt-next.testdevops.ru`; сервер: `server3.siteelite.ru`
  (`45.86.39.77`). Адрес — рабочее предложение, до создания DNS нужно проверить,
  что именно он свободен в зоне Reg.ru и в ISPmanager.
- Действующий `chat-volt.testdevops.ru`, подключение виджета на MODX,
  `220volt.testdevops.ru` и production Supabase не менять. Это **копия кабинета**,
  а не переключение рабочего сайта или перенос данных.
- Сборка кабинета сейчас обращается к тому же проекту Supabase
  `yngoixmvmxdfxokuafjp`. Поэтому изменение настроек, базы знаний, пользователей
  или ключей из нового кабинета немедленно повлияет на работающего бота. До
  отдельного решения о тестовой базе допускаются только вход и чтение.

## Подготовка без влияния на действующий сервис

1. Зафиксировать Git commit, текущий URL и доступность старого кабинета.
   Сохранить предыдущее проверенное содержимое нового docroot или номер его
   предыдущего релиза для отката. Не копировать секреты в Git или веб-каталог.
2. Собирать из зафиксированного commit, используя Node 22, `npm ci`,
   `npm test`, `npm run qa:widget-contract`, `npm run qa:widget-loader` и
   `npm run build`. Проверить наличие `dist/index.html`, `dist/embed.js`,
   `dist/widget.js`, `dist/widget-version.js` и `dist/widget-version.json`.
   Для артефакта записать commit SHA и контрольную сумму архива; на сервере
   сверить сумму до публикации.
3. В ISPmanager создать **отдельного владельца сайта** и отдельный сайт/docroot
   для нового имени. Для учётной записи нужен уникальный пароль; способ его
   безопасной передачи и хранения согласовать до создания, не записывать в Git,
   команды и отчёты. Отключить ненужные PHP и shell для владельца сайта.
   SSH-доступ будущему разработчику — отдельное решение с отдельной учётной
   записью/ключом, а не автоматическое следствие публикации кабинета.
   Управлять виртуальным хостом через ISPmanager, не редактируя вручную
   генерируемые конфигурации Nginx/Apache и не затрагивая другие сайты server3.
4. Разложить статический `dist` в отдельном версионированном каталоге и
   переключать только docroot нового сайта на проверенный релиз. Не использовать
   очистку общих каталогов или `rsync --delete` по соседним сайтам. Проверить,
   что сервер отдаёт `index.html` для маршрутов SPA (`/login`, `/widget`,
   `/knowledge`, `/settings` и т. д.), но реальные JS/CSS/JSON и отсутствующие
   файлы не подменяет HTML. Зафиксировать правило fallback в настройке сайта,
   переживающей обновление конфигурации ISPmanager.
5. Для контрактного загрузчика виджета корневой HTML с параметром
   `voltWidgetBootstrap=1` должен ревалидироваться (`Cache-Control: no-cache,
   must-revalidate`); `widget-version.js` и JSON нельзя держать в устаревшем
   кеше. Пять связанных release-файлов (`index.html`, `embed.js`, `widget.js`,
   `widget-version.js`, `widget-version.json`) публиковать как один релиз.
   `embed.js` получает версию через sandboxed iframe с корневым HTML: общий
   `X-Frame-Options: DENY` или CSP `frame-ancestors 'none'` (а также
   `SAMEORIGIN` для стороннего сайта) сломает этот bootstrap. Политику
   встраивания задавать осознанно для разрешённых сайтов и проверять в браузере,
   а не включать blanket-запрет для всего домена.

## DNS и HTTPS

1. Владелец зоны проверяет точное имя `chat-volt-next` в Reg.ru: существующие
   A/CNAME и настройки ISPmanager. Сейчас wildcard зоны может отвечать другим
   IP — это **не** подтверждение, что для нового имени уже есть отдельная запись.
2. Если имя свободно, добавить **только** явную A-запись
   `chat-volt-next.testdevops.ru` → `45.86.39.77` с небольшим TTL (например,
   300–600 секунд, если интерфейс разрешает). Не менять wildcard, записи
   `chat-volt` и `220volt`, NS или MODX. Подождать, пока авторитетные DNS и
   внешние резолверы покажут новый IP.
3. После разрешения DNS выпустить сертификат именно для нового имени через
   ISPmanager; проверить цепочку, имя сертификата и продление. Принудительно
   перенаправлять HTTP на HTTPS. Не вводить учётные данные на временном домене
   или HTTP до проверки TLS.

## Минимальный smoke перед передачей заказчику

- Старый кабинет и действующий виджет по-прежнему загружаются; их DNS и
  подключаемый на MODX `embed.js` не изменились.
- Новый HTTPS-адрес отдаёт артефакты ожидаемого commit. `/login` открывается;
  обновление страницы на защищённом глубоком маршруте не даёт 404 (допустим
  редирект на логин). После входа существующей учётной записью проверяются
  роль, чтение списка и выход; запись настроек/базы знаний не тестируется.
- Проверить браузерную консоль, ошибки CSP/CORS и отсутствие секретов в
  статических файлах. Если используются письма, OAuth или ссылки сброса
  пароля, отдельно проверить допустимые URL перенаправления в Supabase Auth;
  обычный вход email/паролем этого не доказывает.
- На новом адресе отдельно проверить контракт кеша: `index.html` не застывает
  после нового релиза, версия bootstrap совпадает с `widget-version.*` и
  `widget.js`. Проверить, что iframe bootstrap реально загружается на
  разрешённом тестовом сайте и не блокируется заголовками. Не менять MODX
  loader ради этой проверки.

## Откат и критерий выхода из Lovable

Если новый сайт работает неверно, вернуть его docroot на предыдущий
проверенный релиз; при необходимости убрать **только** явную A-запись нового
имени. Из-за DNS-кеша отключение имени не мгновенно, но старый кабинет и
работающий виджет продолжают жить независимо. Не откатывать Supabase или MODX
как реакцию на проблему статической копии.

Публикация кабинета на server3 сама по себе **не означает полный отказ от
Lovable**. В этой ветке frontend-ссылки на него уже убраны из `public/embed.js`,
`public/widget.js`, `src/pages/Integration.tsx` и `index.html`, но это ещё нужно
подтвердить на собранном и опубликованном артефакте. Живые Supabase Edge
Functions остаются отдельной зависимостью: `knowledge-process` требует
`LOVABLE_API_KEY`, а `chat-consultant-v3` умеет использовать Lovable Gateway
при включённом failover. В исходниках также остаются dev-only preview/tagging
компоненты. Изменять backend-зависимости только отдельной проверяемой задачей;
до неё не переключать работающий MODX на новый `embed.js` и не объявлять
миграцию завершённой.
