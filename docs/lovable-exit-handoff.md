# Выход 220volt AI-виджета из Lovable: передача разработчику

Статус на 14 октября 2026 года: **план, не выполненная миграция**. Действующий
`220volt.testdevops.ru` не переключать до прохождения критериев ниже. Основной
`220volt.kz` вне рамок первого переключения.

## Что уже есть и что ещё зависит от Lovable

Исходники находятся в GitHub: `siteelite-ai/clever-client-bot`, ветка `main`.
При проверке 14 октября опубликованные `embed.js`, `widget.js` и
`widget-version.js` совпадали с `public/` в Git; перед выпуском повторно
зафиксировать URL, SHA-256 и commit, так как публикация могла измениться.
Переписывать подбор товаров для переезда не требуется. Git хранит код, но не
заменяет веб-сервер и процесс выпуска.

| Компонент | Сейчас | Цель |
| --- | --- | --- |
| Виджет и React-админка | Публикуются Lovable; MODX подключает `clever-client-bot.lovable.app/embed.js`, который перенаправляет на `chat-volt.testdevops.ru` | Статические файлы на сервере заказчика, сборка и выпуск из GitHub |
| Подбор товаров и серверные логи | Supabase `yngoixmvmxdfxokuafjp`, Edge Function `chat-consultant-v3` | Оставить Supabase; управлять выпуском функции из GitHub, без второго автоматического издателя |
| История текущей вкладки | Хранится самим виджетом в `sessionStorage` браузера с TTL 30 минут | Сохранить прежнее поведение при переносе |
| AI-провайдер | OpenRouter; в v3 возможен включаемый Lovable Gateway failover | Проверить фактические флаги, заменить/отключить Lovable-путь только после проверки отказоустойчивости |
| База знаний и PDF | Админка извлекает текст PDF в браузере и отправляет `add_text`; отдельный серверный маршрут `process_pdf` обращается к Lovable Gateway. При этом `knowledge-process` требует `LOVABLE_API_KEY` даже для `add_text` и других действий | Убрать безусловную проверку ключа; проверить использование `process_pdf`, затем заменить или убрать Lovable-маршрут без поломки загрузки PDF |
| Прокси API | Cloudflare Worker с резервным прямым обращением в Supabase | Может остаться; конфигурацию и права передать разработчику отдельно |

`lovable-tagger` в `vite.config.ts` используется только при разработке. Файлы
`.lovable/` содержат спецификации; удалять их ради независимой работы не нужно.
В `src/pages/Integration.tsx`, `public/embed.js`, `public/widget.js` и тексте
админки остаются адреса/упоминания Lovable. `index.html` ссылается на
Lovable-связанные OG-изображения во внешнем R2-хранилище. Их нужно заменить
вместе с переносом, а не отдельной срочной правкой на действующем сайте.
PDF worker админки загружается с CDN; это отдельная, не Lovable-зависимость,
которую стоит также включить в перечень внешних ресурсов.

## Требуемые права и исходные данные

- GitHub: доступ к репозиторию, настройке Actions, environments и секретов.
- Сервер заказчика: SSH-доступ для отдельного пользователя публикации,
  конфигурация веб-сервера, место для версионированных релизов и TLS-сертификат.
- DNS: возможность создать **отдельный staging-адрес** для нового хостинга.
- MODX: доступ к общему чанку `scripts` (`id=25`) и его актуальный экспорт.
  Перед изменением снять новый бэкап; старый бэкап не считать актуальным.
- Supabase: права на функции, Auth URL Configuration, настройки и секреты;
  значения секретов не помещать в Git, задачу или переписку.
- Cloudflare Worker, OpenRouter и каталог 220volt: владельцы, доступы,
  лимиты, схема выпуска и контакты для инцидента.

Конфигурации сервера, DNS, MODX и Cloudflare Worker **нет в этом репозитории**.
Их нужно инвентаризировать у владельцев; не угадывать по исходникам.

## Порядок работ с точками остановки

1. **Зафиксировать базу.** Записать commit `main`, текущий `widget-…`, версии
   Supabase-функций, URL скрипта в MODX, DNS и заголовки ответов. Сохранить
   экспорт MODX-чанка и независимую копию работающего статического релиза.
   Зафиксировать известные проходящие клиентские сценарии и состояние API/БД,
   чтобы не принять функциональную регрессию за эффект смены хостинга.
   Проверить, не продолжает ли Lovable автоматически развёртывать Supabase
   после merge; двух издателей одной функции быть не должно.
2. **Собрать воспроизводимый артефакт из Git.** В CI использовать закреплённую
   версию Node и `npm ci`, затем `npm test`, проверки release-контракта виджета,
   `npm run build` и Deno-проверки. Публиковать только проверенный `dist/` с
   `index.html`, `embed.js`, `widget.js`, манифестами и ресурсами. Сейчас CI
   проверяет backend/виджет, но не собирает и не развёртывает frontend; пути
   `src/**` не включены в обязательную frontend-проверку.
3. **Развернуть параллельный staging на сервере.** Выдать ему отдельный HTTPS
   origin, не меняя DNS действующего `chat-volt.testdevops.ru`. Настроить
   атомарный выпуск в каталог релизов и переключение указателя `current`;
   предыдущий релиз оставить для немедленного отката. Для React-маршрутов
   нужен SPA fallback, для `/?voltWidgetBootstrap=1` — рабочий `index.html`.
   HTML bootstrap и манифест версии должны ревалидироваться; `embed.js` и
   `widget.js` должны получать согласованную версию по действующему контракту
   `docs/widget-release-cache-contract.md`. Не включать запрет на встраивание
   bootstrap iframe без проверки: загрузчик использует sandboxed iframe с
   сайта магазина. Проверить HTTPS, CSP, MIME-типы, cache headers и консоль.
4. **Устранить оставшиеся Lovable runtime-зависимости.** Сохранить работающий
   путь PDF через `pdfjs-dist` в админке и `add_text`. Проверить, используют ли
   другие клиенты серверный `process_pdf`, и заменить его Lovable Gateway-путь
   или вывести из эксплуатации с учётом этих клиентов. Сделать проверку
   `LOVABLE_API_KEY` условной, чтобы остальные действия не зависели от ключа.
   Проверить текст, URL и PDF-документы. Проверить реальные значения флагов
   failover v3, подготовить альтернативу и тест на недоступность OpenRouter.
   Не отключать резервный маршрут вслепую, если он используется в production.
5. **Проверить staging.** Минимум: загрузка админки и вход, bootstrap/манифест,
   открытие виджета, новый диалог и история, один запрос с товаром, одно
   уточнение, ошибка/повтор соединения, PDF базы знаний, мобильный браузер.
   Сверить ответы и логи с зафиксированной матрицей клиентских регрессий и
   текущим релизом. Для нового origin проверить разрешённые Supabase Auth
   redirect URL. Убедиться, что в сетевых запросах кандидата нет ресурсов
   Lovable, включая `lovable.app`, `*.lovable.dev`, логотип и OG-изображение;
   отдельно пройти загрузку PDF и аварийный AI-маршрут.
6. **Контролируемое переключение.** Сначала заменить только URL `embed.js`
   в MODX на staging origin сервера и проверить `220volt.testdevops.ru`.
   Прежний Lovable URL пока сохранить как отдельный откат. Перед переключением
   повторно проверить его редирект: 14 октября он вёл на
   `chat-volt.testdevops.ru`. Не рассчитывать только на него после будущего
   переноса DNS этого домена. После успешной выдержки
   перенести админ-домен, отключить Lovable-публикацию/синхронизацию и убрать
   его секреты. Откат после DNS-переезда — переключение на сохранённый релиз
   на своём сервере, не ожидание DNS-кеша.
7. **Передать эксплуатацию.** Описать команду выпуска/отката, домены,
   владельцев доступов, мониторинг, трассировку по коду запроса, резервные
   копии и процедуру ротации секретов. Настроить разрешённый GitHub deploy
   только после зелёных проверок и с ручным подтверждением production.

## Критерий «мы больше не зависим от Lovable»

Из GitHub можно независимо собрать, опубликовать и откатить виджет, админку и
Supabase-функции; пользовательский трафик, обработка PDF и аварийный AI-маршрут
не обращаются к Lovable; у заказчика есть все права и инструкция для нового
разработчика. До выполнения всех трёх условий объявлять переезд завершённым
нельзя. Supabase, OpenRouter и Cloudflare остаются отдельными сервисами — это
не «переезд всего на один сервер».

[защищённые окружения GitHub Actions](https://docs.github.com/en/actions/reference/workflows-and-actions/deployments-and-environments),
[развёртывание Supabase Functions из GitHub](https://supabase.com/docs/guides/functions/examples/github-actions),
[Auth redirect URL](https://supabase.com/docs/guides/auth/redirect-urls).
