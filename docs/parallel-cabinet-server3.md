# Параллельный кабинет 220volt на server3

## Границы этого этапа

- Новые адреса: кабинет `chat-volt-next.testdevops.ru` и API
  `api-volt-next.testdevops.ru`; сервер: `server3.siteelite.ru`
  (`45.86.39.77`). Оба сайта созданы в ISPmanager, а обе явные A-записи
  подтверждены у авторитетных DNS Reg.ru и внешнего резолвера.
- Действующий `chat-volt.testdevops.ru`, подключение виджета на MODX,
  `220volt.testdevops.ru` и production Supabase не менять. Это **копия кабинета**,
  а не переключение рабочего сайта или перенос данных.
- Владелец выбрал **отдельную тестовую базу**. Первоначальная сборка
  `3d691309871e` содержала production Supabase и поэтому была недопустима
  для входа. Сейчас её docroot сохранён для отката, а на новом сайте
  установлена проверенная изолированная сборка из Git-коммита
  `212f975e8bd9` с URL `api-volt-next.testdevops.ru` и отдельным публичным
  ключом. Правило Nginx по-прежнему возвращает `503` до HTTPS и полного
  браузерного smoke. Рабочий Supabase, прежний кабинет и MODX не менялись.
- В текущей бесплатной организации Supabase уже два активных проекта. Новый
  постоянный hosted-проект или branch нельзя планировать как бесплатную
  операцию; платный тариф требует отдельного решения владельца. Самостоятельный
  Supabase на общем server3 — другой проект с отдельными резервными копиями,
  обновлениями и эксплуатационными рисками, а не простой заменой URL.
- Владелец выбрал самостоятельный тестовый Supabase **на server3**. Отдельный
  стек `volt220test` запущен на выделенных сети и томах: 11 сервисов проходят
  healthcheck, gateway доступен только на `127.0.0.1:18081`. Применены
  48 проверенных миграций приложения и две дополнительные миграции
  безопасности **только для тестовой базы**. Рабочие пользователи, данные и
  секреты не переносились. DNS готов, но до HTTPS, тестовой учётной записи и
  полного smoke браузерный вход и публичное использование не начинать.
- Read-only preflight server3: Docker 29.8.1/Compose 5.5.1, 47 ГиБ доступной
  RAM и 697 ГиБ на `/var`, но уже 205 работающих контейнеров и заполненный
  swap 8/8 ГиБ. Порт `127.0.0.1:18080` занят CrowdSec; `18081` свободен на
  момент проверки. Поэтому нужны отдельный Compose project/network, лимиты
  CPU/RAM/PID и наблюдение за сервером до/после старта. Не подключаться к
  существующей `sites-db-net` и не публиковать порт БД.

## Условия для отдельной тестовой базы

1. После read-only preflight server3 создать **новый** изолированный стек с собственными URL,
   публичным ключом, Auth, базой и Edge Functions. Зафиксировать идентификатор
   цели до любой миграции или деплоя. `supabase/config.toml` в репозитории
   указывает на production; не запускать `supabase db push` или деплой функций
   по этой конфигурации без проверки цели. Использовать закреплённую версию
   официального Docker Compose, отдельный каталог/Compose project/volume и
   секреты вне Git; API gateway привязать только к loopback для существующего
   Nginx, Postgres и Studio напрямую в Интернет не открывать. До запуска
   предусмотреть резервное копирование и лимиты ресурсов общего сервера.
   Выбранные границы шаблона: root-owned каталог
   `/var/lib/volt220-test-supabase/upstream`, данные только внутри выделенного
   `docker/volumes/` этого каталога, Compose-проект `volt220test`,
   Nginx → `127.0.0.1:18081`. Никаких общих томов или `sites-db-net`.
   `/opt` находится на разделе с 25 ГиБ свободного места; поэтому базу и
   Storage размещать на разделе `/var` с 697 ГиБ свободного места.
   На старте — только синтетические данные; перед
   любыми реальными данными нужен зашифрованный внешний бэкап и проверка
   восстановления. В существующей системе автоматический бэкап нового проекта
   не обнаружен.
2. Сверить историю миграций с фактической схемой. `knowledge_chunks` нужна для
   поиска и обработки базы знаний, но не создаётся текущими миграциями;
   восстановить её по проверенной production-схеме, включая индексы и RLS,
   отдельной ревьюированной миграцией. Ещё одно подтверждённое расхождение:
   первоначальная миграция создаёт `knowledge_entries.embedding` как
   `vector(1536)`, а в production фактически `vector(768)`, как и у
   `knowledge_chunks`. Исправлять это только на пустой новой таблице с явной
   проверкой размерности; рабочую таблицу не переписывать. Не угадывать DDL
   по frontend-типам. После применения проверить обе размерности SQL-запросом
   и выполнить реальный `add_text` → chunk → search RPC smoke. Отдельно
   проверить старый `search_knowledge(vector(1536))`: активный v3 использует
   новые гибридные RPC, но этот legacy-вызов не следует считать рабочим для
   нового `vector(768)` без отдельного теста или вывода из эксплуатации.
3. Создать только синтетические тестовые данные и отдельного test-admin.
   Production-пользователей, переписку, журналы, настройки с секретами и
   реальные клиентские данные не копировать. Учесть, что регистрационный
   триггер назначает новому пользователю роль `viewer`.
4. Все обращения кабинета, превью, управления пользователями и `widget.js`
   должны использовать **одну и ту же** тестовую конфигурацию без fallback на
   production Supabase/Cloudflare proxy. Проверять итоговый `dist`, а не только
   исходники; при отсутствующей конфигурации self-host build должен падать.
   Стандартный CI-артефакт `dist/` остаётся production-совместимым и **не
   предназначен для этого нового сайта**. Публиковать только отдельно собранный
   и проверенный `dist-selfhost-test/` с реквизитами тестового backend.
5. Раздельная база не изолирует каталог 220volt и OpenRouter. Для чат-тестов
   использовать отдельные минимально привилегированные ключи и лимиты либо
   заглушки; до этого разрешать только проверки входа/навигации без платных
   запросов. В тестовый backend установлена версия `knowledge-process`,
   которая не требует `LOVABLE_API_KEY` для обычных текстовых действий; только
   legacy-действие `process_pdf` остаётся недоступно без него.
   `knowledge-process` берёт ключ OpenRouter из тестовой
   `app_settings`, а не из переменной окружения; без отдельного лимитированного
   ключа даже `add_text` не пройдёт построение embedding. Каталог в v3 тоже
   требует отдельного решения о тестовом токене или заглушке до чат-smoke.
6. Импорт базы знаний по URL и sitemap на общем server3 нельзя открывать
   только на основании предварительной проверки DNS: между проверкой и
   соединением возможна смена адреса (DNS rebinding). Для первого тестового
   выпуска установить `SELFHOST_TEST_MODE=true` и
   `KNOWLEDGE_REMOTE_IMPORT_ENABLED=false`; текстовые операции базы знаний
   остаются доступны. Включать удалённый импорт только после отдельного
   egress-ограничения и проверки. Это ограничение не должно менять поведение
   рабочего production-кабинета.

## Подготовка без влияния на действующий сервис

1. Зафиксировать Git commit, текущий URL и доступность старого кабинета.
   Сохранить предыдущее проверенное содержимое нового docroot или номер его
   предыдущего релиза для отката. Не копировать секреты в Git или веб-каталог.
2. Собирать из зафиксированного commit, используя Node 22, `npm ci`,
   `npm test`, `npm run qa:widget-contract`, `npm run qa:widget-loader` и
   `npm run build`. Проверить наличие `dist/index.html`, `dist/embed.js`,
   `dist/widget.js`, `dist/widget-version.js` и `dist/widget-version.json`.
   Для артефакта записать commit SHA и контрольную сумму архива; на сервере
   сверить сумму до публикации.
3. В ISPmanager создан отдельный владелец `volt220cabinet` и отдельный сайт
   `chat-volt-next.testdevops.ru`; shell отключён, право SSL включено, PHP для
   сайта отключён. Случайный пароль владельца был передан CLI только через
   переменную окружения и не выводился/не сохранялся. При необходимости
   администратор ISPmanager задаёт новый пароль; не передавайте его в Git.
   SSH-доступ будущему разработчику — отдельное решение с отдельной учётной
   записью/ключом, а не автоматическое следствие публикации кабинета.
   Генерируемый ISPmanager виртуальный хост не редактировался; параметры сайта
   менять через панель и после каждого изменения повторять проверки.
4. Первоначальная сборка commit `3d691309871e` и ISPmanager-страница сохранены
   соответственно в `data/releases/3d691309871e` и
   `data/releases/panel-initial-20261014`. Старый docroot перед переключением
   перемещён в `data/releases/pre-isolated-docroot-20261014`. Новый отдельный
   frontend собран из commit `212f975e8bd9`, архив имеет SHA-256
   `8869d713225e3b8e75b3e3b88d21e5a84d8ae44746ae2144600875c2aca50ace`;
   проверенная копия лежит в `data/releases/212f975e8bd9-selfhost`, а её
   копия атомарно перемещена в docroot только нового сайта под maintenance.
   На сервере проверены файлы, новый API URL и `nginx -t`; снаружи сайт всё
   ещё возвращает `503`. Для следующего релиза сохранять тот же порядок и
   предыдущий docroot, не использовать очистку общих каталогов или
   `rsync --delete` по соседним сайтам. После снятия maintenance проверить,
   что сервер отдаёт `index.html` для маршрутов SPA (`/login`, `/widget`,
   `/knowledge`, `/settings` и т. д.), но реальные JS/CSS/JSON и отсутствующие
   файлы не подменяет HTML. Правило находится только в новом site-specific
   include `/etc/nginx/vhosts-resources/chat-volt-next.testdevops.ru/parallel-cabinet.conf`
   (исходник — `deploy/nginx/parallel-cabinet.conf`). После выпуска SSL или
   изменения сайта в панели сверить include и повторить `nginx -t` и HTTP-smoke:
   панель может перегенерировать конфигурацию.
5. Для контрактного загрузчика виджета корневой HTML с параметром
   `voltWidgetBootstrap=1` должен ревалидироваться (`Cache-Control: no-cache`);
   `widget-version.js` и JSON нельзя держать в устаревшем
   кеше. Пять связанных release-файлов (`index.html`, `embed.js`, `widget.js`,
   `widget-version.js`, `widget-version.json`) публиковать как один релиз.
   `embed.js` получает версию через sandboxed iframe с корневым HTML: общий
   `X-Frame-Options: DENY` или CSP `frame-ancestors 'none'` (а также
   `SAMEORIGIN` для стороннего сайта) сломает этот bootstrap. Политику
   встраивания задавать осознанно для разрешённых сайтов и проверять в браузере,
   а не включать blanket-запрет для всего домена.

## DNS и HTTPS

1. Владелец зоны проверяет точные имена `chat-volt-next` и `api-volt-next` в
   Reg.ru: существующие A/CNAME и настройки ISPmanager. Wildcard зоны может
   отвечать другим IP — это **не** подтверждение, что отдельные записи готовы.
2. Если оба имени свободны, добавить **только** две явные A-записи
   `chat-volt-next.testdevops.ru` и `api-volt-next.testdevops.ru` →
   `45.86.39.77` с небольшим TTL (например, 300–600 секунд, если интерфейс
   разрешает). Не менять wildcard, записи `chat-volt` и `220volt`, NS или MODX.
   Подождать, пока авторитетные DNS и внешние резолверы покажут новый IP.
3. После разрешения DNS выпустить отдельные сертификаты для кабинета и API
   через ISPmanager; проверить цепочки, имена и продление. Принудительно
   перенаправлять HTTP на HTTPS. Не вводить учётные данные на временном домене
   или HTTP до проверки TLS. Gateway Supabase оставить только на loopback за
   HTTPS reverse proxy, не публиковать Docker-порты напрямую.

По состоянию на 14.10.2026 оба авторитетных DNS-сервера Reg.ru и `1.1.1.1`
возвращают `45.86.39.77` для **обоих** новых имён. Попытка создать временный
домен ISPmanager завершилась ошибкой
`temporary_domains(unavailable_domain)` без создания сайта; сам сайт затем
создан без временного домена. На локальном резолвере Mac ещё кэшировался
старый wildcard `45.86.39.5` с оставшимся TTL около 20 часов, поэтому до
истечения кэша для проверки нового сервера использовать точный IP/Host override
и не считать локальный старый ответ ошибкой новой A-записи.
Поверх сайта временно установлен только для нового
домена `/etc/nginx/vhosts-resources/chat-volt-next.testdevops.ru/00-maintenance.conf`
с `return 503;` для всех путей, кроме `/.well-known/acme-challenge/`
(исходник `deploy/nginx/parallel-cabinet-maintenance.conf`);
предыдущая версия этого правила сохранена рядом как
`00-maintenance.conf.bak-20261014` и не попадает в `*.conf` include. После
установки выполнены `nginx -t` и reload; извне подтверждены `503` для `/` и
`/login`, `404` для несуществующего ACME-токена (путь разрешён), а старый
кабинет продолжил отвечать `200`.
Отдельный API-сайт создан с обработчиком `handler_not_used` и без PHP;
его собственный include
`/etc/nginx/vhosts-resources/api-volt-next.testdevops.ru/00-maintenance.conf`
(исходник `deploy/nginx/parallel-api-maintenance.conf`) тоже возвращает `503`
вне ACME-пути. `nginx -t` и reload прошли; снаружи подтверждены `503` для
API `/`, `404` для отсутствующего ACME-токена и `200` для старого кабинета.
Под maintenance установлен отдельный `10-api-proxy.conf` (исходник
`deploy/nginx/parallel-api-proxy.conf`): он разрешит только Auth, REST и три
точных Edge Function path, не открывая Studio/root. После установки Nginx
прошёл повторный синтаксический тест; API `/`, Auth и функция по HTTP всё ещё
возвращают `503`, ACME-путь — `404`, старый кабинет — `200`.
Это намеренный барьер, не ошибка релиза. Под ним развёрнут отдельный
Supabase `volt220test` с 50 миграциями и ровно тремя функциями
(`chat-consultant-v3`, `admin-users`, `knowledge-process`) плюс `_shared`;
официальный пример `hello` перемещён в закрытый каталог для обратимого отката.
Все 11 контейнеров здоровы, предварительные OPTIONS для трёх функций дают
`200`, а вызовы `admin-users` и `knowledge-process` без Bearer-токена — `401`.
Убрать maintenance только после установки изолированной frontend-сборки,
HTTPS, тестовой учётной записи и повторной проверки прав; сохранить правило
как быстрый способ закрыть новый сайт при откате. **HTTPS, вход и публичный
запуск пока не проверены.**

## Минимальный smoke перед передачей заказчику

- Старый кабинет и действующий виджет по-прежнему загружаются; их DNS и
  подключаемый на MODX `embed.js` не изменились.
- После подключения *отдельного* тестового Supabase и снятия maintenance новый
  HTTPS-адрес отдаёт артефакты ожидаемого commit. `/login` открывается;
  обновление страницы на защищённом глубоком маршруте не даёт 404 (допустим
  редирект на логин). Войти **тестовой** учётной записью, проверить роль,
  чтение списка и выход. Production-пользователей, данные и ключи не копировать
  в тестовый проект без отдельного решения.
- Проверить браузерную консоль, ошибки CSP/CORS и отсутствие секретов в
  статических файлах. Если используются письма, OAuth или ссылки сброса
  пароля, отдельно проверить допустимые URL перенаправления в Supabase Auth;
  обычный вход email/паролем этого не доказывает.
- На новом адресе отдельно проверить контракт кеша: `index.html` не застывает
  после нового релиза, версия bootstrap совпадает с `widget-version.*` и
  `widget.js`. Проверить, что iframe bootstrap реально загружается на
  разрешённом тестовом сайте и не блокируется заголовками. Не менять MODX
  loader ради этой проверки.

## Откат и критерий выхода из Lovable

Если новый сайт работает неверно, сначала вернуть site-specific maintenance
`503`; затем вернуть его docroot на предыдущий проверенный релиз. При
необходимости убрать **только** явную A-запись нового имени. Из-за DNS-кеша
отключение имени не мгновенно, но старый кабинет и работающий виджет продолжают
жить независимо. Не откатывать production Supabase или MODX как реакцию на
проблему статической копии.

Перед выдачей репозитория стороннему разработчику проверить, действует ли
исторический токен каталога, записанный в миграции Git; если действует —
ротировать его в системе-источнике. Удаление строки из текущего файла не
удаляет значение из истории Git.

Публикация кабинета на server3 сама по себе **не означает полный отказ от
Lovable**. В этой ветке frontend-ссылки на него уже убраны из `public/embed.js`,
`public/widget.js`, `src/pages/Integration.tsx` и `index.html`, но это ещё нужно
подтвердить на собранном и опубликованном артефакте. Живые Supabase Edge
Functions остаются отдельной зависимостью: рабочая `knowledge-process` пока
требует `LOVABLE_API_KEY` для всех действий; в этой ветке обычные действия
от него отвязаны, но legacy `process_pdf` всё ещё требует ключ. Кроме того,
`chat-consultant-v3` умеет использовать Lovable Gateway при включённом
failover. В исходниках также остаются dev-only preview/tagging
компоненты. Изменять backend-зависимости только отдельной проверяемой задачей;
до неё не переключать работающий MODX на новый `embed.js` и не объявлять
миграцию завершённой.
