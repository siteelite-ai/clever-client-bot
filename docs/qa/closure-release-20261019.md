# Closure candidate, 19 October 2026

Scope: the existing Lovable widget and Supabase `chat-consultant-v3`. The paused server3 migration, public widget loader, and legacy API deployments are not changed.

## Evidence and correction

- Production v461: eight selected customer prompts completed once each without transport failures. Seven are recorded in [the v461 report](reports/closure-targeted-production-v461-20261019.json), with 21/21 independently verified product pages. The eighth, DN027B analogs, completed with four cards under request `2eea4103-f590-4f8b-b91b-29685cd8b686`; those four pages were not independently checked.
- The old household-motion assertion required three cards but accepted the word “бытовой” in a description as equivalent to the catalog's `Вид светильника`; it therefore passed two `для ЖКХ` cards. A separate catalog check found only one in-stock, under-4,000-₸ card in the strict household class: Gauss HALL 20W. Two other non-ЖКХ cards in that price range are classed as industrial. The acceptance assertion now requires primary-class proof on every card and **still requires three cards**. Thus the customer's several-options requirement remains open with current verified inventory; an honest one-card answer is safer but is not a formal PASS. We must not silently redefine the client's expectation.
- The candidate gives a source-proven live class priority over a prose-only application alternative. This priority is category-neutral, applies before shortfall recovery counts and at final render, and retains the existing mandatory per-card gate. A fallback in another catalog class remains possible only when no exact-class card is present. The visible reasoning now states that ordering.
- The TTU 10-mm response contained broken punctuation and a split numeric size already in the model's reasoning step. A generic guard removes only visibly corrupted sentences before either visible output or downstream search contracts, including structured measurement evidence; it does not guess corrected measurements.
- Isolated closure preview: [v46 targeted report](reports/closure-preview-v46-targeted-20261019.json) confirmed the three-product assertion failure while returning exactly one household card; TTU 10 mm and black double sockets passed. The [v47 household report](reports/closure-preview-v47-household-20261019.json) verified one Gauss card and an explicit shortfall under a briefly relaxed fixture. Independent review rejected that relaxation; **do not count its formal PASS as customer acceptance**. These are one-run targeted checks, not a full repeated customer suite.
- Final isolated preview [v48 targeted report](reports/closure-preview-v48-targeted-20261019.json): TTU 10 mm and black double sockets PASS, household motion **FAIL solely because 1 verified exact-class card < the customer's 3-card minimum**; 9/9 product pages verified, no connection error across these three runs. The TTU explanation still had a different malformed delimiter run (`Значения,,,,,`), so the general complete-message guard was extended. [v49 TTU rerun](reports/closure-preview-v49-ttu-20261019.json) passed with four 12/6 cards, 4/4 pages verified, and no malformed delimiter sentence.

Initial local gates: 229 actionability/output/criteria/recovery tests, 101 acceptance-runner tests, Edge type check, and `git diff --check` passed after independent review corrections. At that point the candidate still needed CI, PR review, and a small production smoke after merge/deploy.

## Remaining limitations and release guardrails

- Boiler UPS: v461 gave safe guidance without cards, and the current catalog search did not find a source-proven UPS. The early safety route did not query the catalog; if a suitable UPS is added later, that route will still refuse it. This needs a separate safety-and-catalog integration, not an unverified card in this release.
- Public spend admission currently runs in `observe`, not `enforce`. The deployed route authentication setting must be checked separately from `supabase/config.toml`; the browser's public anon key is not an anti-abuse control, and the widget can reach Supabase directly as well as via the proxy. Legacy `chat-consultant`, `chat-consultant-v2`, and `search-products` endpoints remain active; their consumers have not been ruled out. V1's per-isolate, forwarded-IP limiter is not a global cap, and comparable protection was not found for V2 or `search-products`. Do not disable endpoints or enable a global cap without per-endpoint invocation evidence, measured thresholds, direct-and-proxy tests, and an explicit cutover test. An OpenRouter account limit remains the immediate financial backstop; it is not an API abuse control.
- The eight-prompt check did not establish 3× stability, full customer-suite closure, or all security outcomes. The strict household-motion multi-choice case remains unsatisfied because the verified catalog has one fitting card under the stated constraints. Do not present it as closed.

Follow-up release gate: keep production v463 and the published widget unchanged until the new preview counterexamples, CI, and review pass. After merging the follow-up PR, deploy only `chat-consultant-v3`, verify its new version, and check TTU 10 mm on `220volt.testdevops.ru`; the untouched paths and the household shortfall remain documented by the v463 smoke. If the new function regresses, redeploy the v463 code from `b9e8f06f` and revert the follow-up PR; no database migration is part of this candidate. Admission enforcement and legacy-route changes require a separate security release.
