# Дополнительный релизный контроль: площадь комнаты ≠ форма товара

Сохранённый ответ закрытого preview v178 формально прошёл прежний сценарий люстры, хотя на продолжении «А есть другие варианты?» в `selection_contract.mandatory_criteria` появился фильтр «Форма люстры = квадрат». Клиент указал «30 квадратов» как площадь комнаты и не выбирал форму товара. Поэтому одного количества карточек недостаточно для оценки этого сценария. У ответа HTTP 200, код запроса `093d0057-3043-49f6-8df7-490fddcd71ca`, одна карточка и пустой массив `failures`; обязательный критерий был `{ "key": "Форма люстры", "op": "eq", "value": "квадрат", "evidence": "derived_required" }`.

В draft PR #120 проверяются три пути ошибки: модельное `required_facet_values`, повторная проекция фасета из текста рассуждения и модельный `retrieval_query` без ID фасета. Последний путь может скрыто сузить поиск, даже когда `mandatory_criteria` пуст. Локальная правка расширена до проверки происхождения признака в текущей реплике и серверно подтверждённой активной теме: описание комнаты или старого товара не должно становиться обязательной формой нового товара, а отрицание не должно подавлять следующий явный выбор. Центральная граница каталогового ввода-вывода также проверяет текст запроса, фасеты и категорию; при неподтверждённой форме она переходит к более широкому поиску с сохранением подтверждённых технических условий. Это не означает, что свободный русский язык доказан для всех формулировок: при неоднозначности обязательный фильтр запрещён, нужен широкий поиск или уточнение.

Локальный общий прогон текущей рабочей копии 22.10.2026: 1 758 тестов общего модуля, 141 тест реального HTTP/SSE-обработчика и 356 Node QA-тестов прошли; типизация Edge и целостность закреплённого реестра V9 прошли. Новая офлайн-фикстура действительно вызывает прямой модельный `search_catalog` и проверяет фактические URL `/products`: модельные `query`, `pagetitle`, `category`, `options`, `anchor_leaf_category`, нижнюю цену и номер страницы, а также отсутствие неподтверждённого признака в видимом ответе. Внутренний жаргонный поиск проходит тот же контроль, при этом положительный случай «кукуруза» → CORN сохранён. При отсутствии таксономии модельный точный поиск разрешён только для идентичности, подтверждённой запросом клиента, и отбрасывает все дополнительные фильтры. Дополнительно проверены наследование формы старого товара при замене, отрицание условий комнаты и техническая ось «Формат». Закрытый `chat-consultant-v3-closure-preview` обновлён из runtime-коммита `d3812d18ee681c404623abe3cbc1e746a3d2089c`: Management API 22.10.2026 подтвердил v184, bundle SHA `6bad7d403145848c73b661961a8931fd8d7cb9c25905e7c2b374ac061fd1e9f6`, `verify_jwt=true`; production `chat-consultant-v3` остаётся v575 с прежним bundle SHA. Для предыдущего v183 сохранён отдельный временный backup, но до выпуска требуется проверенный долговременный план отката. Это **ещё не приёмка и не релиз**: результаты сценария пока офлайн, живая матрица не запускалась. Резервный пред-discovery SSE-путь покрыт чистым контрактным тестом и проверкой подключения функции, но не достижимой в текущей фикстуре отдельной HTTP/SSE-трассой.

После успешного бесплатного preflight **аутентифицированного каталожного адреса, который реально использует V3**, нужно выполнить `scripts/qa/area-shape-provenance-prospective.json` на точном кандидате закрытого preview и на том же endpoint, что и полную V9. Публичный HTTP 500 от `220volt.testdevops.ru/api/categories` сам по себе не доказывает отказ рабочего `220volt.kz/api` с токеном. Это отдельный обязательный контроль перед выпуском, а не изменение закреплённых файлов V9. Секрет preview передаётся только через переменную окружения `VOLT220_V3_QA_SECRET`, не в командной строке, отчёте или переписке. Management API допускает чтение списка секретов, но создание новой краткоживущей QA-пары вернуло HTTP 403. Read-only сверка того же PAT с профилем и организацией подтвердила роль **Developer**, а для записи Edge Secrets требуются Owner/Administrator и соответствующее право; оба имени неудачного запуска отдельно проверены как отсутствующие. До предоставления права либо установки секрета уполномоченным администратором живой контроль остаётся `NOT_RUN`.

Приёмка дополнительного сценария требует одновременно:

1. Все четыре точные клиентские реплики завершились без ошибки.
2. Первая выдача содержит 3–5 новых проверенных карточек для гостиной с подтверждённой площадью освещения ≥ 30 м².
3. Последняя выдача содержит 1–5 других проверенных SKU с теми же ограничениями назначения и площади.
4. В последнем `mandatory_criteria` нет фасета формы, выведенного из числовой площади, а в тексте ответа нет навязанного условия «Форма люстры: квадрат».
5. Офлайн HTTP/SSE-тест подтверждает, что и с модельным ID фасета, и без него фактический запрос каталога не сужается по выдуманной форме; отдельные положительные контроли сохраняют явный выбор формы, в том числе при склонении значения фасета. Тест должен охватывать прямой модельный tool-call, `category`/`category_in`, актуальную discovery, перенос подтверждённых технических фильтров и номер страницы после расширения запроса, а также видимый промежуточный и финальный текст.

Текущий JSON-контракт валидируется офлайн-тестом `scripts/qa/price-ranking-acceptance.test.mjs`; он сверяет формулировки всех четырёх реплик с закреплённым клиентским сценарием. Скрытый поисковый запрос невозможно надёжно оценить только по публичному тексту и `selection_contract`, поэтому отдельно обязателен `destination-area-followup-real-handler_test.ts` с проверкой фактических параметров `/api/products`. `validate-release-evidence-v9.mjs` проверяет **только** 190 прогонов / 280 ходов основной матрицы и не засчитывает этот дополнительный отчёт автоматически. При финальном sign-off потребуются оба результата, три реально подтверждённых аналога DN027B, проверка публичной защиты и отдельный браузерный smoke после публикации. До успешного бесплатного preflight рабочего аутентифицированного каталожного адреса платный сценарий не запускать.
