# PR #121: граница включения серверного продолжения

**Состояние:** NO-GO для runtime и production. Миграции и gateway в PR #121
создают только отключённую основу. `chat-consultant-v3/index.ts` не импортирует
gateway или новый проектор контракта. Новый чистый проектор
`conversation-selection-snapshot.ts` проверяет, что успешный завершённый лог
той же темы переносит исходный запрос, обязательные критерии и URL уже
показанных карточек через два информационных уточнения к четвёртому запросу
«А есть другие варианты?». Детерминированный тест без OpenRouter доказывает
структуру переноса и отказ при чужой теме, истечении срока, неподтверждённом
логе и повреждённом контракте; он **не** доказывает поведение живого бота.
У зафиксированного production-сценария `selection_contract.mandatory_criteria`
пуст: этот проектор не превращает такой лог в пригодный контракт и сам по себе
не исправляет четвёртый ход.

## Почему нельзя просто подключить один вызов в обработчике

1. В текущем протоколе виджета есть `sessionId`, но нет отдельного случайного
   bearer темы и версии. `sessionId` задаётся браузером и не может разрешать
   чтение серверного состояния. Для работы gateway виджет должен хранить
   выданный сервером bearer, передавать его и версию с каждым новым запросом,
   устойчиво обновлять их при replay и смене темы, не выводя bearer в
   диагностике, логах и URL.
2. SQL `begin_chat_v3_conversation_turn` требует, чтобы `chat_v3_topic_id`
   был записан **при создании** новой строки `chat_request_logs`. Сейчас
   `claimTurnLogStart` вставляет строку без этой привязки. Поздний `UPDATE`
   нарушит защитный триггер и откроет гонку с повтором `messageId`.
3. `finalize_chat_v3_conversation_turn` признаёт только уже сохранённый
   успешный лог с `diagnostic: complete` и `done`. Следовательно, порядок
   строго такой: сохранить SSE в журнал → заново прочитать завершённую строку
   по server claim → построить снимок только из неё → выполнить CAS-finalize.
   Ошибки, тайм-ауты и разрыв соединения не имеют права менять состояние.
4. Текущий автоматический `new_task` может определяться уже **после** claim
   и частично после классификации. Для новой темы нужно согласовать момент
   SQL-rotation, новый bearer и `session_id` до привязки следующего лога;
   нельзя смешивать старую SQL-тему с новым браузерным диалогом.
5. Даже после подключения нельзя считать URL из предыдущего ответа
   разрешением к показу. Это только исключения для нового поиска. Каждая
   дополнительная карточка должна заново пройти поиск и все обязательные
   критерии. Если последняя выборка не содержит доказанного контракта,
   продолжение должно просить полный запрос, а не запускать свободный поиск.

## Минимальный целостный выпуск отдельным PR

- Добавить версионированный widget↔v3 протокол bearer/version и защищённое
  хранение на клиенте; старые клиенты должны оставаться на прежней ветке.
- В серверном entrypoint: `resolve/create` до INSERT claim, атомарная привязка
  topic id, `begin` до платной работы, только `begun` разрешает её; replay,
  stale version, expired и busy завершаются без второго вызова OpenRouter.
- На успешном завершении прочитать durable log, извлечь проверенный снимок,
  выполнить `finalize` по fence/version; при неуспехе `abort` или fail-closed.
  Новый топик должен создавать чистое состояние, не наследуя прежний подбор.
- Только затем подать снимок в общий selection route как
  `base_request + mandatory_criteria + excluded_urls`, не как свободный
  текст истории и не как подсказку модельной прозе. Старый off-path сравнить
  побайтно по публичным событиям.

**Гейт перед переключением:** disposable PostgreSQL concurrency/RLS тесты;
детерминированные четыре хода с подменой bearer/session/history, истечением
и гонкой двух запросов; preview 3× с реальными карточками и QA-оракулом;
затем лишь отдельное решение о staged rollout и rollback. Пока эти этапы
не пройдены, PR #121 нельзя представлять как исправление четвёртого хода.
