Для двух сбоев люстры коды запроса — `db442741-7dff-4f61-8a95-47714e18862e` и `058a483d-c74d-40ef-9499-c747a365588e`. В `chat_request_logs.steps` оба запроса завершились `v3_product_measurement_correction_failed` с `upstream_unavailable` (502) **до** `search_catalog`. Значит, эти два ответа не позволяют оценить качество поиска других люстр. Статус 502 мог прийти от провайдера либо быть назначен адаптером при непригодном ответе; текущая диагностика их не различает. Требуется проверить устойчивость повторной проверки параметра и добавить безопасное различение этих причин.

Повторный read-only SQL-запрос к этим двум точным ID подтвердил: в сохранённых `steps.meta` есть `upstream_status=502`, но `upstream_origin`, `observed_http_status`, `upstream_provider`, `provider_failed_over` и `primary_http_status` отсутствуют. Это свойство **старых production-логов**, а не доказательство источника ошибки. После установки диагностического закрытого preview v170 агрегатный запрос не нашёл ни одного нового `v3_product_measurement_correction_failed` в `chat_request_logs`; получить происхождение 502 из уже имеющихся записей нельзя. Текущий список функций Supabase по-прежнему показывает production `chat-consultant-v3` v572 и закрытый preview v170. Нужен один авторизованный адресный четырёхходовый прогон preview с чтением только служебных полей завершающего лога; повторный production-запрос не заменит эту проверку.

Кодовый разбор выявил системную предпосылку: первая выдача сохранила `selection_contract.mandatory_criteria: []`, а проверка «максимальная площадь освещения ≥30 м²» во второй реплике сохранилась только как текст. Точечный read-only запрос к завершённому серверному логу первой реплики `105a2754-d50b-48d1-b571-82144191311a` подтвердил, что полный `selection_contract` содержит только `hash`, пустые `mandatory_criteria` и `result_cardinality`: назначение «в зал/гостиную» в нём также не структурировано. В четвёртой реплике условие площади снова выводится моделью вместо повторного использования серверного доказательства. Безопасное исправление должно сохранять **весь** проверенный контракт исходного подбора (включая назначение, измерение и ограничения доступности), затем перепроверять каждый критерий на свежих карточках. Сохранить только порог площади было бы небезопасно: такая ветка могла бы выдать люстру для другой комнаты. Пробную неопубликованную интеграцию именно поэтому полностью сняли; если полного доказательства нет, действующий защитный отказ остаётся.

В PoE-ответе поле бренда `U/UTP` для товаров GENERICA/ITK повторяет данные [карточки GENERICA](https://220volt.kz/catalog/kabeli%2C-provoda-i-izdeliya-dlya-prokladki-kabelya/kabel-i-provod/kabel-utp%2C-ftp/kabel-vitaya-para-uutp-kat.5e-100mgcz-4-paryi-ldpe-outdoor-1m-chernyij-generica/) и [карточки ITK](https://220volt.kz/catalog/kabeli%2C-provoda-i-izdeliya-dlya-prokladki-kabelya/kabel-i-provod/kabel-utp%2C-ftp/itk-vitaya-para-futp-kat.5e-4x2x24awg-ldpe-chernyij-%28305m%29-iek-%28up.%29/). Это дефект исходных каталожных данных, а не доказанная выдумка виджета.

Отдельная бесплатная повторная проверка 18/18 уникальных карточек **первой серии** по живым страницам подтвердила канонический адрес, SKU, текущую цену в тенге и общий признак наличия. Восемь отличий сокращённых названий API от названий страниц не меняют идентичность товара. Этот контроль **не** подтверждает остаток по конкретному городу и историческую цену на момент ответа, а также не заменяет проверку технических параметров каждого сценария.
