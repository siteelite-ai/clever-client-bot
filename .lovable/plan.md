# Проверка draft PR #47 до merge: возможен ли безопасный branch-preview

## Короткий ответ

Безопасного способа проверить именно commit `c5ae53dc` из ветки `fix/sse-lumen-contract-20260903` до merge — внутри этого проекта нет. Ни миграцию, ни `chat-consultant-v3-preview` нельзя развернуть из GitHub-ветки, не затронув то, что запрещено трогать.

## Почему (проверенные факты)

- Рабочее дерево проекта соответствует ветке по умолчанию (последний коммит `728f079a`), файла `supabase/migrations/20260903120000_chat_request_idempotency.sql` в дереве нет: последняя миграция — `20260810114133_...`. Значит применить миграцию из PR можно только после того, как код ветки окажется в рабочем дереве (то есть после merge/переключения ветки), либо вручную скопировав SQL — это уже изменение main-дерева.
- `supabase/functions/chat-consultant-v3-preview/index.ts` — это одна строка: `import "../chat-consultant-v3/index.ts";`. Preview не имеет своего исходника. Чтобы preview проверял код PR, нужно изменить `chat-consultant-v3` — то есть ровно ту production-функцию, которую менять запрещено. Изолированного preview-кода не существует.
- Деплой функций в этом проекте выполняется платформой из рабочего дерева, а не из произвольного git-ref. Заявленных ограничений (`functions list` → 403 у CLI, MCP без `projects:write`, Drafts без Git sync и без backend-деплоя до Accept) достаточно, чтобы исключить и внешний путь: нет канала, который бы взял именно `c5ae53dc` и развернул одну функцию.
- Миграции в Supabase применяются к единственной базе проекта. Отдельной preview-БД в проекте нет, поэтому «применить миграцию только для preview» технически невозможно — она сразу становится общей с production.

Единственное, что реально можно сделать до merge без риска, — статическая проверка: прочитать diff PR на GitHub и убедиться, что миграция additive (только `CREATE ...`/`ADD COLUMN ... NULL`/`CREATE UNIQUE INDEX ... IF NOT EXISTS`, никаких `DROP`/`NOT NULL`/переименований) и что изменения виджета не попадают в опубликованный статический бандл. Это чтение, без применения.

## Минимально рискованный порядок merge → deploy → rollback (не выполняется, только описание)

1. Pre-merge (read-only): вычитать diff `c5ae53dc` — подтвердить additive-характер миграции, отсутствие изменений в `public/widget.js`/`widget-version.json`, отсутствие правок в `chat-consultant`/`chat-consultant-v2`.
2. Зафиксировать точку возврата: текущий коммит default-ветки (`728f079a`) и версия миграций (`20260810114133_...`) — как целевой откат.
3. Применить миграцию отдельным шагом, до деплоя функций. Additive-миграция обратно совместима: старая версия функции продолжает работать с новой схемой. Проверить, что таблица/индекс появились и что существующие запросы `chat_request_logs` не сломались.
4. Merge PR в default-ветку. Дать платформе задеплоить функции; сразу после деплоя проверить SSE-поток в инкогнито (без кэша виджета) на одном контрольном кейсе.
5. Наблюдение 15–30 минут: `chat_request_logs` (доля `error`, `total_ms`) и логи edge-функции. Критерий отката — рост ошибок или таймаутов против baseline.
6. Rollback кода: revert-коммит PR в default-ветке → повторный деплой функций. Миграцию откатывать не нужно и не рекомендуется: additive-объекты безвредны для предыдущей версии кода. Если откат схемы всё же понадобится — отдельной обратной миграцией (`DROP INDEX`/`DROP TABLE`), только после подтверждения, что новый код больше не задеплоен.
7. Feature flag как страховка: если PR вводит новое поведение, безопаснее вести его через флаг в `app_settings` (по аналогии с `v3_*_enabled`), чтобы после деплоя включать и выключать без нового деплоя.
