# Переход ключей интеграций из браузера на сервер

Этот документ — контроль выпуска, а не инструкция включить режим без проверки. Пока серверные читатели и админка используют `app_settings`, одно лишь ограничение RLS не скрывает значения от браузера администратора. Добавление нового хранилища само по себе эту проблему не закрывает.

## Инварианты

- Три интеграционных ключа — каталог, OpenRouter и Google — не возвращаются в браузер после переключения. Админский API отдаёт только признак настройки, принимает замену/удаление и выполняет проверку модели на сервере.
- Все потребители (V1, V2, V3, поиск товаров, обработка и поиск базы знаний) используют один серверный контракт. В режиме `private-required` нет скрытого возврата к старым колонкам или переменным окружения.
- Режим по умолчанию — `legacy`; новый код до отдельного переключения не меняет работающего бота. Переключатель нельзя выбирать запросом клиента. Секреты Supabase общие для проекта, поэтому один глобальный переключатель не изолирует preview от production.
- Значения ключей, даже сокращённые, не попадают в логи, ошибки, отчёты CI, браузерные ответы или тестовые фикстуры. Для сверки допустимы только признаки наличия и совпадения, без значений.
- Не меняются не-секретные настройки виджета и право администратора управлять ими.
- Совместный одноразовый PostgreSQL-гейт PR № 125 читает точные байты миграции прав PR № 122 из закреплённого коммита `96d69abf926718a39e63ea16d10478204efbd430` и проверяет blob `459d1776d495618373103c6cb7bdf463a7cd1c25`. Если PR № 122 меняется, до релиза нужно обновить оба pin и заново выполнить гейт; отсутствие объекта или несовпадение — ошибка, а не пропуск проверки. Это не заменяет проверку действующих прав и не запускает production cutover.

## Порядок выпуска и проверяемые ворота

1. **Аддитивная база и код.** Применить миграцию отдельного хранилища с RLS и явным запретом доступа `anon`/`authenticated`/`PUBLIC`. Доказать на PostgreSQL 16, что чтение и запись доступны только серверной роли. Опубликовать админский Edge API, оставив все потребители в `legacy`, а новый интерфейс выключенным.
2. **Подготовка без раскрытия.** В серверной транзакции перенести текущие значения из `app_settings` в новое хранилище. Сверить наличие и совпадение на сервере; не копировать ключи вручную через браузер, CLI-вывод или чат. Для этого этапа нужен уполномоченный администратор проекта.
3. **Закрытый preview.** Явно включить `private-required` только для его серверного bundle; проверить отсутствие fallback, авторизацию админского API, замену/очистку ключа, модельный ping и запросы каталога. Проверить поведение всех логических веток по точечным тестам. Не использовать один проектный env-флаг для preview и production.
4. **Согласованное переключение.** Лишь после доказанной совместимости перевести все live-потребители на `private-required` и включить новый интерфейс. Затем обнулить старые три поля, защитить их от повторной записи со стороны `authenticated`, сохранив редактирование остальных полей. Проверить сетевые ответы браузера, что исходные ключи отсутствуют.
5. **Ротация.** Каталожный токен, ранее записанный литералом в миграции Git, заменить у его издателя и отозвать старый после проверки нового пути. То же сделать для других ключей, если аудит обнаружит их прежнее раскрытие. Удаление строки из текущего файла не удаляет её из Git-истории.
6. **Финальная приёмка.** Два набора доказательств обязательны: безопасность ключей и все клиентские/регрессионные сценарии живого каталога. Зелёный CI или один успешный запрос не равны полной приёмке.

## Откат

До обнуления старых полей откат — возврат server-side режима `legacy` и прежнего интерфейса. После обнуления сначала серверной транзакцией восстановить старые поля из защищённой копии, затем вернуть прежние bundles/интерфейс. Это временно восстанавливает прежний риск раскрытия ключей в браузере, поэтому допустимо только как аварийный откат с последующим повторным переходом. Если старый ключ уже отозван у издателя, его нельзя восстанавливать как рабочий; использовать только актуальное значение.

Ни одна из этих фаз сама по себе не разрешает релиз: каталог должен быть доступен, обязательные аналоги подтверждены, а вся приёмка пройдена.
