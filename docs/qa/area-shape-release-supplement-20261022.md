# Дополнительный релизный контроль: площадь комнаты ≠ форма товара

Сохранённый ответ закрытого preview v178 формально прошёл прежний сценарий люстры, хотя на продолжении «А есть другие варианты?» в `selection_contract.mandatory_criteria` появился фильтр «Форма люстры = квадрат». Клиент указал «30 квадратов» как площадь комнаты и не выбирал форму товара. Поэтому одного количества карточек недостаточно для оценки этого сценария. У ответа HTTP 200, код запроса `093d0057-3043-49f6-8df7-490fddcd71ca`, одна карточка и пустой массив `failures`; обязательный критерий был `{ "key": "Форма люстры", "op": "eq", "value": "квадрат", "evidence": "derived_required" }`.

Кандидат в draft PR #120 закрывает три пути ошибки: модельное `required_facet_values`, повторную проекцию фасета из текста рассуждения и модельный `retrieval_query` без ID фасета. Последний путь мог скрыто сузить поиск до квадратных люстр, даже когда `mandatory_criteria` оставался пустым. Контроль формы и стиля действует по живым фасетам и доказательству запроса клиента, а не по специальному правилу для люстр. Явная просьба о квадратной форме или стиле по-прежнему работает. Это локально проверено unit-тестами и офлайн HTTP/SSE-тестом полного обработчика; живой preview не подтверждён.

После восстановления каталога и развёртывания **точного коммита-кандидата** в закрытый preview нужно выполнить `scripts/qa/area-shape-provenance-prospective.json` на том же endpoint, что и полную V9. Это отдельный обязательный контроль перед выпуском, а не изменение закреплённых файлов V9. Секрет preview передаётся только через переменную окружения `VOLT220_V3_QA_SECRET`, не в командной строке, отчёте или переписке.

Приёмка дополнительного сценария требует одновременно:

1. Все четыре точные клиентские реплики завершились без ошибки.
2. Первая выдача содержит 3–5 новых проверенных карточек для гостиной с подтверждённой площадью освещения ≥ 30 м².
3. Последняя выдача содержит 1–5 других проверенных SKU с теми же ограничениями назначения и площади.
4. В последнем `mandatory_criteria` нет фасета формы, выведенного из числовой площади, а в тексте ответа нет навязанного условия «Форма люстры: квадрат».
5. Офлайн HTTP/SSE-тест подтверждает, что и с модельным ID фасета, и без него фактический запрос каталога не сужается по выдуманной форме; отдельный положительный контроль сохраняет явный выбор квадратной формы.

Текущий JSON-контракт валидируется офлайн-тестом `scripts/qa/price-ranking-acceptance.test.mjs`; он сверяет формулировки всех четырёх реплик с закреплённым клиентским сценарием. Скрытый поисковый запрос невозможно надёжно оценить только по публичному тексту и `selection_contract`, поэтому отдельно обязателен `destination-area-followup-real-handler_test.ts` с проверкой фактических параметров `/api/products`. `validate-release-evidence-v9.mjs` проверяет **только** 190 прогонов / 280 ходов основной матрицы и не засчитывает этот дополнительный отчёт автоматически. При финальном sign-off потребуются оба результата, три реально подтверждённых аналога DN027B, проверка публичной защиты и отдельный браузерный smoke после публикации. Пока каталог не проходит бесплатный preflight, платный сценарий не запускать.
