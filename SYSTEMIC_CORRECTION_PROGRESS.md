- [-] **3. Единый контракт намерения и критериев**
  - Ввести типизированный контракт: товарный класс, применение, ограничения, бюджет, количество результатов и происхождение каждого критерия.
  - Разделить требования пользователя, безопасные вычисления, предположения и каталожные факты.
  - Запретить неподтверждённым предположениям становиться обязательными фильтрами.
  - Готово, когда ложные критерии вроде «для ЖКХ» не появляются без запроса пользователя.
  - Добавлено происхождение критерия: явное условие пользователя, обязательный вывод, подтверждённый факт каталога или предположение модели.
  - Предположение модели теперь может направить первичный поиск, но не попадает в неизменяемый обязательный контракт и не исключает товары без подтверждения клиента.
  - Явные отрицательные условия клиента сохраняются отдельно и остаются обязательными.
  - Финальное совпадение характеристик карточек больше не может само создать новое обязательное условие; контракт отдаёт происхождение каждого обязательного критерия.
  - Приёмочная матрица автоматически отклоняет карточки без контракта происхождения и критерии с происхождением «предположение модели» или «факт каталога».
  - Любая ветка, отдающая карточки, теперь обязана отправить машинный контракт; отсутствие обязательных критериев представляется честным пустым контрактом, а не скрытым состоянием.
  - Прямой поиск точной составной маркировки отдаёт явный пользовательский критерий `3×1,5`; preview-проверка пройдена дважды.
  - Общее слово больше не повышает составное каталожное значение до требования клиента: все значимые части значения должны быть подтверждены запросом. Это устраняет ложную привязку к «ЖКХ» без товарного словаря.
  - Явное назначение в конструкции `для …` компилируется только в уникальное значение живого фасета. Preview 430 трижды подтвердил контракт `Philips + офисно-административное освещение`; неоднозначное или отсутствующее значение не превращается в фильтр.
  - Общий морфологический гард больше не считает любую замену одной буквы доказательством: `светом` не может включить фасет `свеча`. Технические коды с визуально похожими кириллическими/латинскими символами нормализуются единообразно (`Е27` = `E27`).

- [-] **4. Связка «рассуждение → поиск → проверка → выдача»**
  - Поиск должен исполнять тот же контракт, на котором основано объяснение.
  - Проверить привязку чисел, единиц и свойств: В, А, кВт, фазы, полюса, цоколи, сечения и размеры.
  - Не допускать подмены товарного класса: лампа/светильник, силовой/слаботочный кабель и т. п.
  - Готово, когда правильное рассуждение приводит к соответствующим товарам или честному уточнению.
  - Для успешной выдачи без текста провайдера сервер строит видимое обоснование только из уже проверенного товарного класса и обязательного контракта.
  - Preview 421 подтвердил появление видимого обоснования и машинного контракта у пяти карточек; проверка сценария гостиной остановлена внешней квотой.
  - Preview 430 подтвердил сквозную связку назначения: фраза клиента `для офиса` → живой фасет `Вид светильника = офисно-административное освещение` → поиск с брендом Philips → две карточки, прошедшие тот же контракт.
  - Preview 433 устранил подмену класса в аналогах без словаря товаров: полное описание источника и его живое таксономическое пространство замораживаются до поиска кандидатов. Сценарий лампы GX53 прошёл 3× за 2,3–2,6 секунды, каждый раз вернул четыре лампы и ни одного светильника.
  - Точный счёт в одном фасете теперь сверяется и с видимой составной маркировкой: при `ровно 1 полюс` карточка `1П+Н` отклоняется, даже если старый структурный фасет каталога хранит её как `1`. Сценарий 25 A / C / 1П прошёл 3×.
  - Preview 437 сквозным контрактом связал явные `3000 K`, `тёплый`, `E27` и `светодиодная` с поиском и карточками. Сценарий прошёл 3×: четыре лампы E27/3000 K, без ложной `свечи` и без лишнего внешнего AI-вызова.

- [-] **5. Количество, ранжирование и уточняющие вопросы**
  - Единообразно обрабатывать «самый дешёвый», «несколько», «варианты» и «все позиции».
  - При недостатке результатов расширять поиск только внутри того же товарного класса и без снятия обязательных условий.
  - Не спрашивать уже указанные параметры и не требовать от покупателя лишней технической теории.
  - Готово, когда количество карточек и уточнения соответствуют запросу во всех товарных категориях.
  - Подтверждён общий, не привязанный к категории контроллер количества: «самый дешёвый»/«один» → 1; обычный подбор → цель 4, минимум 3; «несколько/варианты» → цель 5, минимум 3; «все» → расширенная выборка до 8; явное число → указанное число в безопасном диапазоне.
  - До финального ограничения контроллер расширяет окно поиска и проверяет до 15 кандидатов для цели 5, поэтому отсеянные карточки могут быть заменены следующими подходящими без ослабления критериев.
  - Каждый товарный ответ теперь содержит машинный контракт `result_cardinality` с полями `target`, `minimum`, `mode`, `explicit`; он добавляется и к прямым веткам, которые обходят основной agent-loop.
  - Приёмочные сценарии для светильников, розеток, автоматов, удлинителей и одиночного суперлатива проверяют не только фактическое число карточек, но и решение контроллера о требуемом количестве.
  - Preview 423 подтвердил контракт одиночного суперлатива на живом API: одна точная карточка, `target=1`, `minimum=1`, `mode=single`, 5 065 мс. Preview 426 трижды подтвердил многотоварный контракт: пять карточек, `target=5`, `minimum=3`, `mode=alternatives`.
  - Множественный суперлатив больше не схлопывается до одной карточки. Если строгий каталог подтверждает меньше желаемого минимума, критерии не ослабляются: preview 430 трижды вернул все две офисные позиции Philips и явно сообщил о дефиците относительно цели 4.
  - Прямой запрос `покажи все позиции` сохраняет расширенную кардинальность после очистки командной части точной маркировки: preview 431 трижды вернул восемь точных ВВГ 3×1,5 с контрактом `target=8/minimum=3/mode=exhaustive`.
  - Остаётся системная работа по уточнениям: текущий ранний readiness-слой содержит предметные профили. До финала его нельзя считать универсальным; нужно заменить либо ограничить его общей проверяемой политикой «какой недостающий параметр действительно меняет совместимость/диапазон выбора» и живыми фасетами.
  - Точно заданный availability-запрос больше не блокируется необязательным вопросом о уже указанном параметре; сценарий `3000 K + E27` сразу переходит к каталогу.
